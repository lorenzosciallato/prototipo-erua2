## AREA 1 — MONITORAGGIO ATTIVO E ALLERTING
 
### 1.1 Cosa monitorare
 
| Categoria | Cosa monitorare | Soglia di allarme | Azione |
|---|---|---|---|
| **Accessi** | Tentativi di login falliti per stesso utente | >5 in 10 minuti | Allerta, possibile attacco a credenziali |
| **Autorizzazione** | Tentativi di accesso a risorse altrui (403) | >10 in 5 minuti | Allerta, possibile tentativo IDOR |
| **Traffico** | Richieste totali | >media giornaliera × 3 | Allerta, possibile DDoS o attacco di saturazione |
| **Errori** | Errori 500 (server) | >5 in 5 minuti | Allerta, possibile bug o attacco |
| **Latenza** | Tempo di risposta API | >2 secondi per 5 richieste consecutive | Allerta, possibile degrado o attacco |
| **Backup** | Backup notturno | Non completato entro le 2:00 | Allerta, perdita di copia di sicurezza |
| **Spesa** | Costo dei servizi a consumo | >70% del budget mensile | Allerta, possibile attacco economico |
 
### 1.2 Implementazione del monitoraggio
 
**Con i servizi gestiti**, la maggior parte del monitoraggio è già disponibile. Devi solo configurare gli alert.
 
**Esempio per Supabase (PostgreSQL)**:
 
```sql
-- Query per monitorare tentativi di accesso anomalo (da eseguire ogni 5 minuti)
SELECT 
    user_id,
    COUNT(*) as failed_attempts,
    MIN(created_at) as first_attempt,
    MAX(created_at) as last_attempt,
    COUNT(DISTINCT ip_hash) as distinct_ips
FROM login_attempts
WHERE success = false
  AND created_at > NOW() - INTERVAL '10 minutes'
GROUP BY user_id
HAVING COUNT(*) > 5;
 
-- Se la query restituisce risultati → allerta
```
 
**Esempio per monitoraggio API (Node.js)**:
 
```javascript
// Middleware di logging con metriche
app.use((req, res, next) => {
    const start = Date.now();
    res.on('finish', () => {
        const duration = Date.now() - start;
        const status = res.statusCode;
        const path = req.path;
        const method = req.method;
        const user_id = req.user?.id || 'anonymous';
        
        // Log strutturato
        const log = {
            timestamp: new Date().toISOString(),
            method,
            path,
            status,
            duration,
            user_id,
            ip_hash: hash(req.ip)
        };
        
        // Log su sistema di monitoraggio (es. Axiom, Datadog, o file)
        logger.info(log);
        
        // Se la durata è anomala, allerta
        if (duration > 2000 && status === 200) {
            alert('API slow response', { path, method, duration, user_id });
        }
    });
    next();
});
```


- **Per il monitoraggio delle prestazioni**: strumenti integrati nel provider (es. Vercel Analytics).

## AREA 2 — AGGIORNAMENTI DI SICUREZZA
 
### 2.1 Processo di aggiornamento
 
**Obiettivo**: patchare vulnerabilità note entro 24 ore dalla pubblicazione dell'advisory.
 
**Fasi**:
 
1. **Monitoraggio delle advisories**:
   - PostgreSQL security mailing list.
   - Node.js/Python security advisories.
   - Librerie utilizzate (via `npm audit` o `pip-audit`).
   - Provider cloud (Supabase, Vercel, AWS).
 
2. **Valutazione**:
   - La vulnerabilità interessa il sistema? (es. una vulnerabilità in una funzione non utilizzata).
   - Qual è il rischio? (critica, alta, media, bassa).
   - Esiste già una patch?
 
3. **Patching**:
   - Applicare la patch su ambiente di test.
   - Eseguire i test di sicurezza (IDOR, autenticazione, sanitizzazione).
   - Se i test passano, applicare in produzione.
   - Se i test falliscono, valutare workaround o rollback.
 
4. **Verifica**:
   - Testare la funzionalità interessata.
   - Monitorare gli errori per 24 ore.
 
### 2.2 Automazione degli aggiornamenti
 
**Script di controllo automatico** (da eseguire quotidianamente):
 
```bash
#!/bin/bash
# security_check.sh
 
# Controlla aggiornamenti PostgreSQL
# (se usi un servizio gestito, il provider li applica automaticamente)
 
# Controlla vulnerabilità delle librerie Node.js
npm audit --json > npm_audit.json
if grep -q '"severity":"critical"' npm_audit.json; then
    echo "CRITICAL vulnerability found in Node.js dependencies"
    # Invia allerta
    curl -X POST $WEBHOOK_URL -d "CRITICAL npm vulnerability found"
fi
 
# Controlla vulnerabilità delle librerie Python
pip-audit --json > pip_audit.json
if grep -q '"critical"' pip_audit.json; then
    echo "CRITICAL vulnerability found in Python dependencies"
    curl -X POST $WEBHOOK_URL -d "CRITICAL pip vulnerability found"
fi
 
# Controlla aggiornamenti del provider (se disponibile via API)
# (es. Supabase, Vercel)
```
 
### 2.3 Workflow di aggiornamento
 
```
1. Advisory pubblicata
   │
   ▼
2. Valutazione: interessa il sistema?
   │
   ├── NO → archivia
   │
   ▼ SÌ
3. Rischio?
   │
   ├── BASSO/MEDIO → pianifica aggiornamento entro 7 giorni
   │
   ▼ ALTO/CRITICO
4. Applica patch su ambiente di test
   │
   ▼
5. Esegui test di sicurezza (RLS, autenticazione, sanitizzazione)
   │
   ├── FALLISCONO → valuta workaround o rollback
   │
   ▼ PASSANO
6. Applica in produzione (con rollback pronto)
   │
   ▼
7. Monitora per 24 ore
```

## AREA 3 — INDIPENDENZA DAI FORNITORI
 
### 3.1 Principio
 
Il sistema non deve dipendere da un singolo fornitore. Ogni servizio critico deve poter essere sostituito con un altro senza riscrivere l'intero sistema.
 
### 3.2 Fornitori critici e alternative
 
| Servizio | Fornitore principale | Alternativa | Note |
|---|---|---|---|
| Database | Supabase (PostgreSQL) | Neon, AWS RDS, self-hosted | Tutti PostgreSQL → migrazione semplice |
| Autenticazione | Supabase Auth | Auth0, Clerk, self-hosted | Magic link è standard → migrazione possibile |
| Storage | AWS S3 / Cloudflare R2 | MinIO, Google Cloud Storage | API S3-compatible → migrazione semplice |
| AI | OpenAI (o fornitori EU) | Anthropic, self-hosted (Llama) | Prompt design → migrazione possibile |
| Email | Resend / SendGrid | AWS SES, Mailgun | SMTP standard → migrazione possibile |
| Hosting | Vercel / Fly.io | Netlify, AWS, self-hosted | Static site + API → migrazione possibile |
 
### 3.3 Implementazione dell'indipendenza
 
**Astrazione del fornitore via interfacce**:
 
```python
# database.py — interfaccia astratta
class DatabaseInterface:
    def get_user(self, user_id): ...
    def save_message(self, message): ...
    def get_conversation(self, conversation_id): ...
 
# supabase_impl.py — implementazione con Supabase
class SupabaseDatabase(DatabaseInterface):
    def __init__(self, client):
        self.client = client
    def get_user(self, user_id):
        return self.client.table('users').select('*').eq('id', user_id).execute()
 
# neon_impl.py — implementazione con Neon (se mai necessario)
class NeonDatabase(DatabaseInterface):
    def __init__(self, connection):
        self.conn = connection
    def get_user(self, user_id):
        # Query con psycopg2
        cursor = self.conn.cursor()
        cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
        return cursor.fetchone()
```
 
**Configurazione tramite variabili d'ambiente**:
 
```python
# config.py
import os
 
DB_PROVIDER = os.getenv('DB_PROVIDER', 'supabase')
 
if DB_PROVIDER == 'supabase':
    from supabase_impl import SupabaseDatabase as Database
elif DB_PROVIDER == 'neon':
    from neon_impl import NeonDatabase as Database
else:
    raise ValueError(f"Unknown DB provider: {DB_PROVIDER}")
 
db = Database()
```
 
**Piano di migrazione**:
 
1. Il sistema funziona con il fornitore principale.
2. L'alternativa è configurata su un ambiente di test con gli stessi dati (o dati fittizi).
3. In caso di necessità, si cambia la variabile d'ambiente e si riavvia il servizio.
4. La migrazione dei dati (se necessaria) è gestita da uno script separato.

## AREA 5 — INCIDENT RESPONSE AVANZATA
 
### 5.1 Scenari non previsti
 
Questa sezione copre gli scenari che i test non hanno previsto. La risposta si basa su principi generali.
 
**Principi di risposta**:
 
1. **Isolare**: interrompere il canale dell'attacco (commutazione in sola lettura, revoca sessioni, bloccare IP).
2. **Analizzare**: capire cosa è successo, quando, a quali dati.
3. **Documentare**: registrare ogni azione con data e ora.
4. **Comunicare**: informare il Titolare immediatamente.
5. **Correggere**: applicare la patch o la modifica necessaria.
6. **Ripristinare**: ripristinare il servizio (con i dati, se compromessi, o senza).
7. **Retrospettiva**: capire come evitare che si ripeta.
 
### 5.2 Playbook per scenari comuni
 
**Scenario A — Sospetto di accesso non autorizzato a dati**
 
1. **Isolare**: commutazione in sola lettura. Revocare tutte le sessioni.
2. **Analizzare**: esaminare i log per identificare:
   - Quali utenti hanno avuto accesso.
   - Quali dati sono stati letti/modificati.
   - Quando è avvenuto.
3. **Documentare**: registrare tutto.
4. **Comunicare**: informare il Titolare immediatamente. Se la violazione è confermata, il Titolare decide la notifica all'autorità e agli interessati.
5. **Correggere**: identificare la vulnerabilità (es. policy RLS errata, token compromesso) e correggerla.
6. **Ripristinare**: ripristinare il servizio.
7. **Retrospettiva**: aggiornare i test per coprire lo scenario.
 
**Scenario B — Attacco di saturazione (DDoS o abuso)**
 
1. **Isolare**: attivare le protezioni del provider (rate limiting, WAF, blocchi IP).
2. **Analizzare**: identificare la fonte dell'attacco (IP, pattern di richieste).
3. **Documentare**: registrare tutto.
4. **Comunicare**: informare il Titolare.
5. **Correggere**: se l'attacco sfrutta una vulnerabilità (es. endpoint costoso senza autenticazione), correggerla.
6. **Ripristinare**: ripristinare il servizio.
7. **Retrospettiva**: aggiornare i limiti di frequenza e i controlli.
 
**Scenario C — Compromissione dell'account di un moderatore/amministratore**
 
1. **Isolare**: revocare tutte le sessioni dell'account. Bloccare l'account.
2. **Analizzare**: esaminare le azioni compiute dall'account compromesso.
3. **Documentare**: registrare tutto.
4. **Comunicare**: informare il Titolare.
5. **Correggere**: rafforzare le politiche di autenticazione (es. 2FA per amministratori, se implementato).
6. **Ripristinare**: ripristinare l'account con nuove credenziali.
7. **Retrospettiva**: valutare l'introduzione di 2FA per ruoli critici.

## AREA 6 — RETROSPETTIVA DI SICUREZZA
 
### 6.1 Obiettivo
 
Migliorare continuamente il sistema sulla base degli incidenti reali e delle lezioni apprese.
 
### 6.2 Processo
 
1. **Registrazione dell'incidente**: descrizione, data, impatto, risoluzione.
2. **Analisi delle cause**: cosa ha permesso l'incidente? (tecnica, procedurale, umana).
3. **Azioni correttive**: cosa si può fare per evitare che si ripeta? (test, codice, procedure).
4. **Assegnazione**: chi implementa le azioni correttive e entro quando.
5. **Verifica**: le azioni correttive sono state implementate e funzionano?
